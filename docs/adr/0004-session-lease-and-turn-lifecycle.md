# ADR 0004: 会话所有权用进程身份判活，回合可中断、可继续

Status: accepted（2026-11-15）rev G：R1–R3 已实现，相关测试 242/242 通过；发布记录见附录 F。版本变化见附录 D。

日期：2026-11-15

## 0 结论

**验收当天只需要三件事不出错：关掉页面不打断、重启后不卡死、卡住时会说话。** 前两件今天一半成立、一半失败；第三件完全不成立。

| 时刻     | 专家动作                 | 今天的表现           | 目标             | 本文做什么     |
| -------- | ------------------------ | -------------------- | ---------------- | -------------- |
| A 并发   | 同一会话连发两条消息     | 顺序执行，不交错     | 保持             | 不改           |
| B 长任务 | 关掉标签页，5 分钟后重开 | 回合继续，重连回填   | 保持             | 不改，写成约束 |
| C 卡住   | 上游不动                 | 永久挂起，界面无信号 | 5 分钟内可见失败 | R1             |
| D 重启   | 平台重启后发消息         | 静默挂起最长 24 小时 | 秒级接管         | R2             |
| E 继续   | 中断后点"继续"           | provider 400 拒绝    | 成功续上         | R3             |

三句结论：

1. **A 和 B 已经成立，不要为它们加设计**——B 需要的是守住，不是修。
2. **D 的根因是判活只看 pid 是否存在；E 的根因是半条 assistant 进了 provider 载荷。**
3. 修法只有三件小事：一个判据、一条载荷规则、一个继续端点。

取舍原则：只解决验收当天真实会遇到的失败。概率接近零的情况（同一人两个标签页、多设备同开会话、跨主机 NFS、时钟漂移）不做设计，只记录在开放问题。真实用户少，宁可给一个清晰的错误，也不要一个静默的等待。明确不做：TTL 续约定时器、自动续跑、OpenAI background 模式、SSE 游标、SQLite 迁移。

## 1 决策

按机制分组，组内按依赖排序。每组开头一句就是该组的结论。

### 1.1 判活（修 D）——把"这个号码有人吗"换成"还是当初那个进程吗"

| #   | 决策                                                                     | 理由                                                                                |
| --- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| D1  | `FileLease.abandoned()` 的判据换成 `ProcessIdentity.owns(pid, identity)` | 判据变准，等待语义不变；48 处调用点一起受益，不新增第二套锁                         |
| D2  | 锁文件增加 `identity`；旧锁无此字段时回退 `running(pid)`                 | 升级期间旧锁仍可用，部署后自然收敛                                                  |
| D3  | **不做 TTL 续约**                                                        | 重启与 pid 复用由进程身份秒级覆盖；唯一剩下的"冻结"用等待预算兜底，不值得引入定时器 |
| D4  | 会话租约等待预算 24 小时 → 120 秒，超时抛可见错误                        | 任何残余等待都不超过两分钟，也不会静默                                              |

### 1.2 可见（修 C）——网络停了要能说话

| #   | 决策                                         | 理由                                |
| --- | -------------------------------------------- | ----------------------------------- |
| D5  | `provider.<id>.options.idleTimeout = 300000` | 零代码；provider 已有能力，默认关闭 |

### 1.3 继续（修 E）——载荷干净，人才能点"继续"

| #   | 决策                                                                 | 理由                                        |
| --- | -------------------------------------------------------------------- | ------------------------------------------- |
| D6  | 中断不写字段，按"最后一条 assistant 无 `completed` 且无 `error`"派生 | 用户主动停止会写 `AbortedError`，天然被排除 |
| D7  | `toModelMessages` 跳过没有 `time.completed` 的 assistant             | 唯一新增的载荷规则，直接修 400              |
| D8  | 继续 = `POST /session/:sessionID/resume` → `loop()`；忙时 409        | 复用 `assertNotBusy`，不新建消息            |
| D9  | 中断可见由客户端派生，复用现有卡片                                   | 状态在内存、重启即丢；派生不需要新持久化    |

### 1.4 守住（B 不改）——三层都不绑定

关掉标签页不中止回合，靠客户端不 abort、传输不订阅连接关闭、运行时由独立回调驱动。任何一层被改成"连接关闭 → 取消会话"，B 就失效。详见 §3.6，用例见 §5。

### 1.5 明确不做

| 不做                         | 理由                                                                     |
| ---------------------------- | ------------------------------------------------------------------------ |
| D10 启动时自动续跑           | 回合本来就不随连接终止；进程真的消失时交给人——自动续跑会在无人在场时花钱 |
| TTL 续约 / bootId 文件       | 进程身份已经覆盖它们要防的故障                                           |
| OpenAI background / SSE 游标 | 上游忽略 `background`；重连回填已存在                                    |
| SQLite 迁移                  | 存储层重构，与本故障不同层                                               |

## 2 证据

### 2.1 生产事故：一条锁把会话挂死两小时以上

| 时间     | 事件                                                          |
| -------- | ------------------------------------------------------------- |
| 15:45:39 | u0003 的会话锁写入 `{pid: 2}`                                 |
| 17:51:58 | 容器重启，pid 2 是**新**进程（starttime 证明复用）            |
| 18:09    | `kill -0 2` 通过；锁仍被视为持有中                            |
| —        | 新消息卡在 `acquire`；`/session/status` 返回 `{}`；界面无提示 |

`abandoned()` 的实现是 `!running(pid)`，而 `running` 是 `process.kill(pid, 0)`——它回答"这个号码现在有人吗"，不是"当初那个人还在吗"。租户容器里应用恒为 pid 2，所以重启后旧锁永远"活着"。

### 2.2 故障实验：四个问题各是什么表现

隔离环境（本地源码启动、数据目录在 `/tmp`），完整记录见附录 C。

| 编号 | 做法                      | 观测                                                                            | 证明了                 |
| ---- | ------------------------- | ------------------------------------------------------------------------------- | ---------------------- |
| E1   | 回合 3 秒后中断客户端     | 服务端继续生成并完成（273 → 720 → 1426 字符）                                   | B 成立，不需要设计     |
| E2   | 回合中途 `kill -9` 后重启 | 留下 440 字符半条；20 秒内无自动恢复；新消息正常完成（18.7s / 2328 字符）       | 进程消失时回合确实会丢 |
| E3   | 写入一条"活人 pid"的假锁  | 请求静默挂起，状态为空；删锁后早已断开的请求继续并完成                          | D 的静默性             |
| E4   | 崩溃后直接 `loop()`       | 新 assistant 生成，但 provider 400：`reasoning_content ... must be passed back` | E 的根因在载荷         |

## 3 设计

### 3.1 判活：一个判据

```text
takeover(path):
  o = read(path)
  if o.identity && !owns(o.pid, o.identity)   → 接管（进程已死，或 pid 被新进程复用）
  if !o.identity && !running(o.pid)           → 接管（旧格式锁）
  否则                                         → 等待（预算 120s，超时抛可见错误）
```

| 故障                 | 判据                          | 恢复时间           |
| -------------------- | ----------------------------- | ------------------ |
| 容器重启、pid 2 换人 | `owns` 为 false               | 秒级（下一次轮询） |
| 进程崩溃             | `owns` 为 false（进程不存在） | 秒级               |
| 进程被冻结           | 判据为"活着"，进入等待        | 120 秒后可见错误   |
| 旧格式锁             | `running(pid)` 回退           | 与今天相同         |

没有 TTL、没有续约定时器、没有 instance 文件。

### 3.2 锁文件与获取

沿用路径 `data/session-loop/<sha256(projectID\0sessionID)>.lock`：

```json
{ "v": 2, "token": "<uuid>", "identity": "<sha256>", "pid": 2, "created": 1794738400000 }
```

获取逻辑保持现状（`O_CREAT|O_EXCL` → 失败则判活 → `rename` 到 `.dead` 后重建），只替换 `abandoned()` 的判据，并在写入时用 `ProcessIdentity.capture(process.pid)` 填充 `identity`。

`capture` 返回 `undefined` 时（受限平台或环境），写入不带 `identity` 的锁，行为回退到今天的 `running(pid)`，记一条日志。

### 3.3 等待预算

`LOOP_LEASE_TIMEOUT` 从 24 小时改为 120 秒。超时错误必须可行动：

```text
Another turn is still running for this session (process 2, holding for 340s).
If that process restarted, restart the container; otherwise wait for it to finish.
```

同进程的第二条消息不会走到这里——`start()` 已把它挂到已有回合的回调上。120 秒只约束跨进程的稀有路径与"活着但停摆"的持有者。

### 3.4 回合状态与载荷

- 派生：最后一条 assistant 既无 `time.completed` 也无 `error` → 回合被中断。
- 用户主动停止会写 `AbortedError`（`message-v2.ts:1458`），不会被当成可继续的回合。
- **载荷规则（唯一一条）**：`toModelMessages` 跳过没有 `time.completed` 的 assistant。`sessionMessages` 是 transcript 全量克隆（`prompt.ts:1515`），未封装前它原样进载荷——这就是 E4 的 400。
- 继续：`POST /session/:sessionID/resume`；`assertNotBusy` 校验，忙则 409（`{error:"busy", status}`）；没有可继续的回合则 400。

### 3.5 客户端

- 显示条件：最后一条 assistant 无 `completed` 且会话不忙 → "运行中断"卡片 + "继续"按钮。
- 状态拉取失败或离线 → 不显示继续，只提示刷新。误判比不提示更伤信任。
- 收到 409 → 刷新状态，不弹错。
- 旧半条输出保留展示，新的 assistant 紧随其后。

### 3.6 关掉标签页不终止回合（不可回归）

这是验收里唯一"已经成立、只需要守住"的时刻。三层缺一不可：

| 层     | 现状                                                          | 位置                     |
| ------ | ------------------------------------------------------------- | ------------------------ |
| 客户端 | `pagehide` / `visibilitychange` 只 flush 滚动位置，不发 abort | `context/layout.tsx:226` |
| 传输   | 消息路由把回合跑完才写响应，不订阅 `c.req.raw.signal`         | `routes/session.ts:792`  |
| 运行时 | abort 来自会话控制器（`/abort`、`cancel()`），不来自连接      | `prompt.ts:497`；E1      |

重连回填也不依赖这条连接：`server.connected` → `refreshLoadedMessages`。

**约束**：不要在 unload 里调 `/abort`，不要让消息路由订阅请求信号，不要让 SSE 断开触发取消。§5 的 L2 用例守这条。

不在本文范围：进程真的消失（容器重启、应用被关、崩溃）。那时留下半条（E2），由用户点"继续"（R3）或重发。

## 4 风险与边界

| 风险                 | 说明                                           | 处理                                                |
| -------------------- | ---------------------------------------------- | --------------------------------------------------- |
| `capture` 不可用     | 受限平台或容器（无 `/proc`）                   | 回退 `running(pid)`，记日志；不存在比今天更差的路径 |
| 冻结的持有者         | 判据认为它活着                                 | 120 秒可见错误；重启容器后身份变化可立即接管        |
| 跨进程长回合         | CLI 在服务端跑长任务时发同一会话               | 120 秒后报错而不是等 24 小时；已知代价              |
| 升级期间的旧锁       | 旧进程写 v1 锁                                 | 回退路径与今天一致，重启后自然收敛                  |
| 连接与回合被重新绑定 | 未来改动静默给 unload 加 abort，或订阅请求信号 | §3.6 的约束 + L2 用例；改这三层前先改本节           |
| 进程消失             | 容器重启、应用被关、崩溃                       | 留下半条，用户点"继续"或重发；自动续跑不做          |
| 网关 keepalive       | 若发心跳，会喂活 `idleTimeout`                 | 需一次抓包（开放问题）                              |
| NFS / 跨主机         | 时钟与 starttime 语义不再可靠                  | 本期不承诺；数据根均为本地盘                        |

## 7 分阶段与工作量

| 阶段 | 内容                                                   | 验收                               |
| ---- | ------------------------------------------------------ | ---------------------------------- |
| R1   | 租户 `idleTimeout=300000`                              | 上游断开 5 分钟 → 可见失败         |

## 8 开放问题

1. 网关是否发送 SSE keepalive，会不会喂活 `idleTimeout`——需一次抓包。
2. 观察一段时间后，如果"冻结的持有者"真实出现，再考虑加 TTL；现在不加。
3. 中断后的半条输出：折叠还是原样展示。
4. 进程真的消失（容器重启、应用被关）时是否需要接住未完成回合：本期不做，未来取决于它实际发生的频率。
